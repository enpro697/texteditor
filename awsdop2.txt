概念の完全な誤解だ。**可視性タイムアウト**とは、「あるLambdaインスタンスがキューからメッセージを取得した際、他の処理系からそのメッセージを一時的に見えなく（不可視に）する保護期間」のことだ。
これを0秒に設定すれば、Lambdaがメッセージを取得した瞬間に、別のLambdaインスタンスからも同一メッセージが見えてしまい、即座に重複処理が乱発する。

(日乃竜胆)
A total misconception of fundamental mechanics. **Visibility Timeout** is the safety window during which a consumed message is hidden from other consumers while being processed.
If set to 0 seconds, the moment an instance grabs a message, other Lambda instances immediately consume the exact same payload, detonating massive duplicate executions across the system.

(蒞星怜空)
さらにLambdaの実行制限時間を縮めれば、DynamoDBが少しでも応答をもたついた瞬間にLambdaが道半ばで首を刎ねられ、処理未完了のゾンビタスクがキューに永遠に滞留し続ける。地獄の無限増殖バグの完成だな。

(蒞星怜空)
Moreover, truncating Lambda's timeout guarantees that the moment DynamoDB hesitates even slightly, the function gets decapitated mid-execution, leaving zombie tasks lingering in the queue forever. An exquisite infinite-duplication loop from hell.

---

(日乃竜胆)
**【不正解の検討 3】**
「Lambdaコード内の例外処理を完全に削除し、エラー発生時は関数を即座にクラッシュさせてデッドレターキュー（DLQ）に全メッセージを直接退避させる」というアプローチ。

(日乃竜胆)
**[Analysis of Incorrect Option 3]**
"Remove all error-handling logic within the Lambda code, allowing the function to crash immediately upon exceptions and routing all messages directly to a Dead Letter Queue (DLQ)."

(月凪惟緒)
あ、DLQってゴミ箱というか救護室みたいなやつだよね？ ダメなら全部そこに投げちゃえば安心……じゃないの？

(月凪惟緒)
Ah, DLQ is like a first-aid quarantine bin, right? If things fail, shouldn't we just dump everything in there for peace of mind...?

(日乃竜胆)
短絡的すぎる。それでは「10件中9件成功していた正常なデータ」の追跡を放棄し、成功分も含めたバッチ丸ごとをDLQに放り込むことになる。
結果として、正常に書き込まれたデータの再選別作業という過大な運用負荷（オペレーショナルオーバーヘッド）が発生し、設問の「最小限の開発・運用工数」という要件に真っ向から反する。

(日乃竜胆)
Far too short-sighted. Doing so abandons tracking the 9 successfully processed records and blindly discards the entire batch into the DLQ.
This creates immense operational overhead to manually deduplicate and salvage valid writes, directly violating the question's mandate for minimal operational effort.

---

(日乃竜胆)
では、真の**正解の選択肢**と、その完全なるアーキテクチャ設計を提示する。

(日乃竜胆)
Now, let us present the definitive **correct solution** and its flawless architectural design.

(日乃竜胆)
**【正解のアーキテクチャ】**

1. **Lambdaのイベントソースマッピング設定で `ReportBatchItemFailures` （バッチ項目失敗のレポート）を有効化する**。
2. Lambdaコード内で各メッセージをループ処理し、DynamoDB書き込みで例外が発生したメッセージのID（`itemIdentifier`）のみをレスポンス配列に詰めて返す。
3. DynamoDB側で **ジッター（ゆらぎ）を伴う指数関数的バックオフ（Exponential Backoff with Jitter）** を適用するか、トラフィック特性に応じて **オンデマンドキャパシティモード** または適切な **Auto Scaling** を構成する。

(日乃竜胆)
**[The Correct Architecture]**

1. **Enable `ReportBatchItemFailures` in the Lambda Event Source Mapping configuration.**
2. Within the Lambda function code, iterate through each message and return only the specific message IDs (`itemIdentifier`) that failed into the batch response payload.
3. Apply **Exponential Backoff with Jitter** for DynamoDB calls, or adopt **On-Demand Capacity Mode** / appropriately configured **Auto Scaling** based on traffic profile.

(月凪惟緒)
出た……！ 『ReportBatchItemFailures』……！ ヒノりん、これって要するにどういう魔法なの？

(月凪惟緒)
There it is...! `ReportBatchItemFailures`...! Hino-rin, what kind of magic does this actually perform in plain terms?

(日乃竜胆)
極めて論理的な仕組みだ。
これを使うと、Lambdaは「10件中、失敗した3番目のメッセージIDだけ」をSQSに返却できる。
SQSは「成功した9件」はキューから正常に削除し、「失敗した1件」だけをキューに残して再試行対象とするのだ。これにより、重複書き込みと無駄なキャパシティ消費が完全に根絶される。

(日乃竜胆)
It is an intensely logical mechanism.
When enabled, Lambda returns only the specific message ID of the failed 3rd item out of 10 to SQS.
SQS then deletes the 9 successful messages from the queue and retains solely the 1 failed message for future retry. This completely eliminates duplicate writes and redundant capacity consumption.

(蒞星怜空)
くくく……さらにバックオフとジッターを噛ませることで、リトライの波が一斉に衝突する「群集事故（Thundering Herd Problem）」を防ぎ、波を綺麗に散らすわけだ。破滅の連鎖を断ち切る、冷徹でエレガントな秩序の勝利だな。

(蒞星怜空)
Kukuku... and by incorporating exponential backoff with jitter, you disperse retry waves, preventing the catastrophic "Thundering Herd Problem" from crushing the database again. A ruthless, elegant triumph of systemic order over chaotic ruin.

(月凪惟緒)
はぁ〜〜……！ 失敗したやつだけを名指しで再テスト受けさせて、合格した優等生は先に帰すシステムってことね。めっちゃスッキリしたかも……！

(月凪惟緒)
Aah~~...! So it's like sending only the one failing student to retake the test while letting all the passing students go home early. That makes total crystal-clear sense now...!

(日乃竜胆)
その理解で相違ない。基本原理を押さえれば、いかなる複雑なクラウドアーキテクチャの設問も恐るるに足らん。復習を怠るなよ、イオち。

(日乃竜胆)
Your understanding is spot-on. Once you grasp these fundamental principles, no cloud architectural problem can stand in your way. Keep this lesson etched in your mind, Iochi.
